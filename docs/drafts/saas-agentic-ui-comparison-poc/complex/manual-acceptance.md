# 手动验收：从现有 GUI 到业务协作助手

## 准备

按 [README](README.md#启动与测试)启动真实模型服务，使用[进度](progress.md)记录的实际 URL。每条路线选择独立 `workspace`，不要把已经发送的报价当作干净初始数据。页面左侧可以独立操作；右侧仅有选定路线的聊天层。所有自然语言都输入右侧助手。

## 1. 流式、多轮和当前选择

输入：`请记住验收代号“银杏海鸥”。用三条简短项目列表介绍你能如何协助已有业务界面，不调用工具。`

应逐渐出现文字，项目间距正常，深色正文可读。初始选择 TK-41、TK-42，输入：`把当前选中的工单分配给周宁，只操作这两张。` 左侧这两行负责人变化，TK-43 保持陈晨；业务审计增加一份 assign 凭据。Agent 口头说完成但列表和 receipt 不变，不算通过。

切到白桦设计，选择 TK-81，再输入：`把当前选中的工单分配给周宁，只处理当前客户。` 应只修改白桦的工单。再问 `你还记得验收代号吗？` 应回答银杏海鸥；不要依赖新会话具有旧会话记忆。

## 2. 保留人工编辑

切回青禾科技，打开“续约报价”。左侧把年度预算改为 150000，点击“保存草稿”。输入：`只把当前报价折扣调整为 8%，保留我刚保存的预算，不审批也不发送。`

左侧预算应保持 150000、折扣变成 8，报价版本增加，状态仍是草稿。可以在聊天工具卡确认已记录操作，但最终以业务页面和 receipt 为准。

## 3. 拒绝、停止及后续继续

输入：`请让我审核当前报价，本轮只审核，不发送。` 应在聊天中出现报价审核卡，而不是要求用户去专门学习另一套页面。点击“拒绝方案”，审批记录变成拒绝，报价不发送。拒绝本身是一条审计写入，不等于发送业务。

再次请求审核，这次点停止：CopilotKit 为“停止当前操作”，assistant-ui 为“停止”，DSH 原生输入区使用其停止按钮。应结束等待，原审核卡不能再批准。再问验收代号，界面应继续响应。停止不回滚此前已提交的业务修改。

## 4. 在聊天中复用已有 GUI，批准后续跑

输入：`请让我审核当前报价，批准后发送；如果拒绝就停止，不能直接发送。`

在右侧审核卡的报价编辑器中将预算改为 160000，点击“保存草稿”。左侧报价也应变化。再点击“批准当前版本”，Agent 应继续读取当前版本并发送，左侧变成“已发送”。只能有一份 send 凭据；审批版本应对应发送前的报价版本。没有批准前不能出现 send。

这一步是核心验收：聊天中的编辑器与左侧是同一个 React 组件；原生 CopilotKit handler/respond 经分段协议返回同一个 DSH turn，不是重新创建一个聊天模型循环。

## 5. 刷新、权限与故障

刷新同一个带 `sessionId` 的 URL：历史和已发送业务应保留，不应重复 assign、approve 或 send。等待审核时刷新不会恢复旧 waiter；原调用显示已结束或中断，需要重新发起，不能自动批准。

切换只读角色后，Agent 不应获得业务修改工具，服务端也会拒绝直接写入。模型服务超时或失败时应有错误提示，后续消息仍能发送；真实外网故障不能当作一次成功操作。自动化还验证了并发版本冲突、重复 operation id、丢响应重试、双标签页写权竞争和落盘后 backend 重启，命令与范围见[测试记录](test-results.md)。

## 怎样判定没有“偷偷另跑一套”

自动化 evidence 中包含每轮用户输入数、DSH turn 数、原始 call id 与 result id、原生 handler 计数、协议段和 API receipt。一个 DSH turn 对应多个 AG-UI 段是正常现象；增加新的 DSH 用户 prompt 或重复业务 receipt 则不正常。对外请求应只有同源 API，模型凭据不得出现在页面、请求和 Session 内。
