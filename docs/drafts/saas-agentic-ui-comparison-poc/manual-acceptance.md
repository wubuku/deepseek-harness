# 手动验收说明

## 开始前

先按 [README](README.md#启动) 启动真实模型服务。分别打开 `ui=native`、`ui=assistant`、`ui=copilot`，各使用新的 `workspace` 参数。不要把 scripted 的确定性输出当作真实模型表现。原生路线首次出现 DSH 预览版说明时点击“继续”。

左侧业务列表、右上“模拟角色”、右侧聊天、聊天内业务表单是验收入口。右下业务凭据计数比模型说“完成了”更可靠；完整事实保存在 backend 的 Session 与 `saas.json`。

## 相同验收故事

1. **手动 GUI 基线。** 点击左侧“新建任务”，输入“GUI 基线任务”，保存。任务列表新增一项，业务凭据增加 1。这证明业务 GUI 不依赖助手即可使用。
2. **流式回复。** 输入：“请用三条项目列表简述如何读取工作台、填写表单、等待人工确认。每条约三十字，不调用工具。” 应在生成过程中逐步看到文字；列表应清晰紧凑，不出现过大的条目间距。
3. **已有表单进入聊天。** 输入：“请创建一个标题为‘比较实验任务’的项目任务，负责人林悦，优先级高。使用已有业务表单让我修改后确认。” 在聊天内把标题改为“用户修改后的任务”，负责人改为“周宁”，保存。左侧出现最终修改值，凭据增加 1；助手不应再次要求确认旧值。
4. **工单处理。** 输入：“请把工单 TICKET-42 分配给周宁，设为高优先级，状态改为处理中。请读取当前版本并让我确认。” 确认后左侧状态变为 `in_progress`、负责人周宁、版本 2，凭据增加 1。
5. **拒绝高风险操作。** 输入：“请审批账单 INV-2026-018，展示现有审批界面让我决定。” 检查金额 ¥12,800，点击“取消操作”。账单仍是 `pending`，凭据不增加，对话继续。
6. **批准。** 输入：“现在我决定批准账单 INV-2026-018。请再次显示审批界面让我确认。” 点击“确认批准”。账单变为 `approved`，版本 2，凭据增加 1。
7. **权限拒绝。** 模拟角色切为“只读”，要求创建新任务。如果模型根据已读取角色直接拒绝，这是正常表现；如果出现表单，保存时 API 必须拒绝。两种情况下任务和凭据都不能增加。切回“可操作”。
8. **会话记忆。** 先说“记住我的验收代号是橙色海豚”，再问“我之前告诉你的验收代号是什么？” 同一 Session 应回答该代号。不要用新会话测短期记忆。
9. **停止后继续。** 再要求新建任务，等待表单出现；不要保存，点击聊天输入区停止按钮。表单应失效，凭据不增加；再发一条普通消息应继续得到回答。
10. **刷新。** 保留 URL 的 `sessionId` 刷新，检查用户消息、已完成工具卡、业务列表仍在。历史卡片不能重新变为可提交表单，也不能新增凭据。

## 额外故障验收

- **版本冲突。** 在聊天打开工单表单并暂不确认；使用左侧“处理工单”先保存一次。再提交旧聊天表单，应显示 `VERSION_CONFLICT`，不得覆盖新版本；对话仍能继续。原生和第三方 UI 共同使用相同版本字段与 API。
- **重复提交。** 连续点击确认不得产生多份业务记录；测试也用同一 operation id 重发 HTTP 请求，要求重放原 receipt。不要用“再次发一条相同自然语言消息”代替幂等测试，后者是新用户意图和新 tool call。
- **双标签。** 第一标签保持同一 Session 打开，第二标签访问带相同 `sessionId` 的 URL。第二标签必须拒绝取得写权或禁用发送，不能静默把消息发给另一个 Session。
- **等待中刷新。** 当前 PoC 不恢复等待中的交互。旧卡应不可提交；业务列表和凭据可核查是否已提交，但自动恢复旧调用未验收。不要把不恢复表单当作已实现可靠后台执行。

## 核对实际业务凭据

服务提供 `GET /api/saas/<workspace>/snapshot` 和 `GET /api/saas/<workspace>/receipts/<operationId>`。助手操作的稳定 operation id 为 `<DSH sessionId>:<DSH callId>`，手动 GUI 操作为 `gui:<uuid>`。一次确认对应一条 receipt；取消、权限拒绝和冲突不创建 receipt。Session 中工具结果的 `toolCallId` 必须与原 `tool/call.data.callId` 一致。
